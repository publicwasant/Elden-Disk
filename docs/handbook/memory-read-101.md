## คำนำ: หนังสือเล่มนี้ตอบคำถามอะไร

คุณเขียนไว้ตอนท้ายแชทว่า *"รู้แค่ว่าอ่าน memory ตอนเกมเปิดอยู่แล้วดึงข้อมูลออกมาได้ … แต่ไม่รู้เลยว่ากระบวนการภายในมันทำงานยังไง … ถ้าเปิดเกมใหม่มันจะไม่ประกาศ address ใหม่จองพื้นที่ใน RAM เรอะ?"*

คำถามหลังสุดนั้น **ถูกต้องเต็มๆ** และเป็นหัวใจของทั้งเล่ม: *ใช่ เปิดเกมใหม่ทีไร object ส่วนใหญ่ถูกจองที่ใหม่* แล้ว tool ของเรายังอ่านได้ เพราะเราไม่ได้จำ "ที่อยู่ของ runes" แต่จำ **"เส้นทาง"** ที่พาไปหา runes ได้ทุกครั้ง เส้นทางนั้นเริ่มจากจุดที่ตำแหน่งคงที่ (`eldenring.exe+0x3B16E30`) แล้วตามลูกศร (pointer) ไปทีละขั้น บทที่ 2, 3 และ 8 จะอธิบายเรื่องนี้ละเอียด

# Part I — พื้นฐาน

## บทที่ 1 — ไบต์ เลขฐานสิบหก และชนิดข้อมูล

### 1.1 หน่วยที่เล็กที่สุด

- **bit** = 0 หรือ 1
- **byte** = 8 bit → ค่าได้ 256 แบบ (0–255)
- คอมพิวเตอร์ไม่มี "ตัวเลข ตัวอักษร ชื่อ ไอเทม" มีแต่ byte ที่ *ตีความ* เป็นอะไรก็ได้ ขึ้นกับว่าโปรแกรมตั้งใจให้อ่านแบบไหน

ประโยคนี้สำคัญที่สุดของบทนี้: **byte ชุดเดียวกันตีความได้หลายแบบ** ตัวอย่างสี่ byte `00 00 F0 41` ตีความเป็น

| ตีความเป็น | ผลลัพธ์ |
|---|---|
| จำนวนเต็ม 32 bit ไม่มีเครื่องหมาย (u32) | 1,106,247,680 |
| ทศนิยม 32 bit (float32) | **30.0** |
| ข้อความ 4 ตัวอักษร | `\0 \0 ð A` (ไม่มีความหมาย) |

ดังนั้นการ "อ่าน memory" ไม่ได้ยากที่การอ่าน byte แต่ยากที่ **รู้ว่าแต่ละตำแหน่งควรตีความเป็นอะไร** ซึ่งคือเหตุผลที่ทั้งโปรเจกต์ต้องมี "แผนที่" (profile) และต้องพิสูจน์ว่าแผนที่ถูก

### 1.2 เลขฐานสิบหก (hex)

hex 1 หลักแทน 4 bit (0–15 เขียนเป็น `0–9, A–F`) ดังนั้น **1 byte = hex 2 หลัก** พอดี จึงเป็นภาษาที่คนใช้อ่าน memory

| ฐานสิบ | hex | หมายเหตุ |
|---|---|---|
| 10 | `0xA` | `0x` คือคำนำหน้าบอกว่าเป็น hex |
| 255 | `0xFF` | ค่ามากสุดของ 1 byte |
| 386 | `0x182` | level ของคุณ |
| 1,000,000 | `0xF4240` | |
| 10,273,265 | `0x9CC1F1` | runes ตอนสแกนรอบสอง |

ออฟเซ็ตที่เราคุยกันทั้งหมดเป็น hex: `0x580` = 1,408 ในฐานสิบ, `0x6C` = 108, `0x3B16E30` = 61,959,728 (ประมาณ 59 MiB จากต้นไฟล์)

### 1.3 Endianness: ทำไมเลขถึง "กลับด้าน"

CPU ตระกูล x86-64 เก็บเลขหลาย byte แบบ **little-endian** = byte ที่มีค่าน้อยสุดมาก่อน

> 📌 **Case File — runes รอบที่สองของ First Scan**
> runes = 10,273,265 = `0x009CC1F1`
> ใน RAM เก็บเป็น: `F1 C1 9C 00` (กลับด้านจากที่เขียน)

นี่คือสิ่งที่ Cheat Engine ทำจริงๆ เวลาเลือก Value Type = **4 Bytes** และพิมพ์ `10273265`: มันแปลงเลขเป็นแพตเทิร์น `F1 C1 9C 00` แล้วไล่หาแพตเทิร์นนี้ใน RAM ทุกจุดที่ address หารด้วย 4 ลงตัว (ตัวเลือก *Fast Scan / Alignment 4* ที่คุณเห็นในหน้าจอ)

### 1.4 ชนิดข้อมูลที่ใช้ในโปรเจกต์นี้

| ชนิด | ขนาด | ใช้เก็บอะไร | Python `struct` |
|---|---|---|---|
| u32 | 4 byte | level, runes, attributes, SpEffect ID | `<I` |
| float32 | 4 byte | duration, timer ของ buff | `<f` |
| pointer (u64) | 8 byte | address ของอีกที่หนึ่ง (บนโปรแกรม 64 bit) | `<Q` |

`<` ใน format string หมายถึง little-endian

**float32** เก็บแบบ IEEE 754: 1 bit เครื่องหมาย + 8 bit เลขชี้กำลัง + 23 bit ทศนิยม

| ค่า | hex | byte ใน RAM | ปรากฏในโปรเจกต์ที่ไหน |
|---|---|---|---|
| 30.0 | `0x41F00000` | `00 00 F0 41` | duration ของ Flame! Grant Me Strength |
| 80.0 | `0x42A00000` | `00 00 A0 42` | Golden Vow |
| 180.0 | `0x43340000` | `00 00 34 43` | Gold-Pickled Fowl Foot |
| −1.0 | `0xBF800000` | `00 00 80 BF` | effect ถาวร (ไม่มีวันหมด) เช่น Gold Scarab |
| 0.1 | `0x3DCCCCCD` | `CD CC CC 3D` | ≈ 0.100000001490… (ไม่ตรงเป๊ะ) |

⚠️ **ทศนิยมแบบ float ไม่ตรงเป๊ะ** 0.1 เก็บไม่ได้พอดี นี่คือเหตุผลที่ tool ปัดเศษ 2 ตำแหน่ง และเหตุผลที่ตัวเลขใน JSON ของคุณลงท้ายแปลกๆ เช่น `21.84`

**pointer** คือเลข 8 byte ที่ *ค่าของมันคือ address* เช่น address `0x7FF3A2CBE970` ถูกเก็บเป็น `70 E9 CB A2 F3 7F 00 00`

### 1.5 อ่าน hexdump แบบมนุษย์

นี่คือหน้าตาของ `PlayerGameData` ช่วง `+0x38` ถึง `+0x77` **จำลองจากค่าจริงใน JSON ของคุณ** (byte ที่ไม่ทราบความหมายจริง ผมแสดงเป็น `00`) โดย address ฐานมาจากการสแกนรอบแรกของคุณ (`7FF3A2CBE9DC − 0x6C`)

```

7FF3A2CBE9A8  +0x38   00 00 00 00  50 00 00 00  3C 00 00 00  3C 00 00 00
7FF3A2CBE9B8  +0x48   5A 00 00 00  5A 00 00 00  0F 00 00 00  3C 00 00 00

7FF3A2CBE9D8  +0x68   82 01 00 00  15 C1 A2 00  00 00 00 00  00 00 00 00
```

| offset | byte | ค่า | ความหมาย |
|---|---|---|---|
| `+0x3C` | `50 00 00 00` | 0x50 = **80** | Vigor |
| `+0x40` | `3C 00 00 00` | 60 | Mind |
| `+0x44` | `3C 00 00 00` | 60 | Endurance |
| `+0x48` | `5A 00 00 00` | 90 | Strength |
| `+0x4C` | `5A 00 00 00` | 90 | Dexterity |
| `+0x50` | `0F 00 00 00` | 15 | Intelligence |

## บทที่ 2 — Process และ Virtual Memory

### 2.1 ทำไมไม่มี "address ของ RAM" ให้ชี้ตรงๆ

ตอนที่เราพูดว่า "address `7FF3A2CBE9DC`" นั่นไม่ใช่ตำแหน่งบนแผงชิป RAM จริง แต่เป็น **virtual address** — ที่อยู่ในโลกส่วนตัวของโปรเซส `eldenring.exe`

หลักการ:

1. ระบบปฏิบัติการให้ *แต่ละโปรเซส* มี **address space** ของตัวเอง เหมือนแต่ละโปรแกรมได้ "ผังเมือง" ของตัวเอง
2. Address `0x7FF3A2CBE9DC` ในโปรเซสเกม กับ `0x7FF3A2CBE9DC` ในโปรเซส Python **เป็นคนละที่กันโดยสิ้นเชิง**
3. ฮาร์ดแวร์ชื่อ **MMU** (Memory Management Unit) แปลง virtual address → physical address ทุกครั้งที่ CPU เข้าถึงข้อมูล โดยใช้ตาราง **page table** ที่ OS ดูแล
4. หน่วยการแปลคือ **page** (โดยทั่วไป 4 KiB = `0x1000`)

แยก virtual address เป็นสองส่วนได้:

> 📌 **Case File** `0x7FF3A2CBE9DC`
> - ส่วน page: `0x7FF3A2CBE` (เลขหน้า) → หน้านี้เริ่มที่ `0x7FF3A2CBE000`
> - ส่วน offset ในหน้า: `0x9DC`

ผลที่ตามมา:

- ตอน **อ่าน memory ของโปรเซสอื่น** เราไม่ได้แตะ RAM ตรงๆ เรา *ขอให้ OS ช่วยอ่านให้* ในนามของโปรเซสเป้าหมาย (บทที่ 5)
- OS จะย้ายข้อมูลระหว่าง RAM กับดิสก์ (paging) เองได้ โดยที่ virtual address ไม่เปลี่ยน — เราจึงไม่สนว่าข้อมูลอยู่ที่ RAM ก้อนไหน

### 2.2 ขอบเขตของ address space (และเหตุผลของ `is_user_ptr`)

บน Windows 64 bit พื้นที่ของโปรแกรมทั่วไป ("user mode") กว้าง 128 TiB (2⁴⁷ byte) ตั้งแต่ `0x10000` ถึง `0x7FFFFFFEFFFF` ส่วนครึ่งบนสุดเป็นของ kernel

เราเอาข้อเท็จจริงนี้ไปใช้ในโค้ดตรงๆ:

```python
USER_MIN = 0x10000            # 64 KiB แรกไม่เคยถูก map: จับ null pointer
USER_MAX = 0x7FFFFFFF0000     # = 2**47 - 0x10000
def is_user_ptr(p): return USER_MIN <= p < USER_MAX
```

ถ้าค่าที่อ่านมาแล้วคิดว่าเป็น pointer อยู่นอกช่วงนี้ (เช่น `0x1234` หรือ `0xFFFFFFFFFFFFFFFF`) **มันไม่มีทางเป็น pointer จริง** tool จึงทิ้ง sample ทั้งก้อน (spec §4.5)

### 2.3 ในโปรเซสมี "ย่าน" อะไรบ้าง

| ย่าน | เก็บอะไร | ลักษณะ address | ตัวอย่างในเรื่องของเรา |
|---|---|---|---|
| **Image** (ตัว exe และ DLL) | โค้ด + ตัวแปร global/static | ตำแหน่งสัมพัทธ์คงที่ต่อ build (บทที่ 3) | `eldenring.exe+3B16E30` |
| **Heap** | object ที่โปรแกรมสร้างตอนรัน (`new`/`malloc`) | เปลี่ยนทุกครั้งที่รัน | `PlayerGameData` ที่ `7FF3A2CBE970` |
| **Stack** | ตัวแปรชั่วคราวของแต่ละ thread | เปลี่ยนเร็วมาก | (ไม่เกี่ยวกับเรา) |
| **Mapped files ฯลฯ** | ไฟล์ที่ map เข้ามา, shared memory | ต่างๆ | — |

แต่ละ page มีสถานะและสิทธิ์: *free / reserved / committed* และ *read / write / execute* ตัวเลือก **Writable** ใน Cheat Engine (ที่คุณเห็นในหน้าจอ Memory Scan Options) คือ "สแกนเฉพาะ page ที่เขียนได้" ซึ่งตัดโค้ดและข้อมูล read-only ทิ้ง ทำให้เร็วขึ้นและผลลัพธ์น้อยลง

> ตอนสแกนครั้งแรก `PlayerGameData` อยู่ที่ `7FF3A2CBE970` (runes ที่ `…E9DC`)
> ถ้าคุณปิดเกมแล้วเปิดใหม่ **ค่านี้ใช้ไม่ได้อีกต่อไป** (จะอยู่ที่อื่น หรืออาจไม่มีอะไรอยู่ตรงนั้นเลย)

แล้ว tool อ่านได้ยังไง? เพราะสิ่งที่คงที่ไม่ใช่ตำแหน่งของ object แต่คือ **ที่ที่เก็บ "ลูกศรชี้ไปหา object"**

**อุปมาห้องสมุด:** หนังสือถูกย้ายชั้นทุกครั้งที่จัดห้องสมุดใหม่ (heap เปลี่ยน) แต่ *ตู้บัตรรายการอยู่ห้องเดิมตำแหน่งเดิมเสมอ* (ตัวแปร global ใน exe) ในตู้มีบัตรบอกว่า "เล่มนี้อยู่ชั้นไหน" และเล่มนั้นก็มีบัตรบอกต่อว่า "ภาคผนวกอยู่หน้าไหน" — เรารู้แค่ที่ตั้งตู้บัตร แล้วไล่บัตรทีละใบ

ในเกม:

```
[ตู้บัตร: ตำแหน่งคงที่]   eldenring.exe + 0x3B16E30   ← ไม่เปลี่ยนตราบใดที่เป็น build เดิม
        │ ค่าที่เก็บอยู่ = address ของ object (เปลี่ยนทุกรอบ แต่ตู้ชี้ถูกเสมอ)
        ▼
   ไล่ตามลูกศร 3 ขั้น → ถึง runes
```

บทที่ 3 อธิบายว่าทำไม "ตำแหน่งในตัว exe" คงที่ และบทที่ 8 อธิบายว่า Pointer Scan หาเส้นทางนี้ได้อย่างไร

## บทที่ 3 — ไฟล์ .exe ในหน่วยความจำ: Module, Image Base, RVA

### 3.1 เมื่อรันโปรแกรม OS ทำอะไร

ไฟล์ `.exe` บน Windows ใช้รูปแบบ **PE (Portable Executable)** ตอนรัน OS *map* ไฟล์เข้า address space เป็นก้อนๆ เรียกว่า **section** โดยหลักๆ คือ

| section | เก็บอะไร |
|---|---|
| `.text` | โค้ดเครื่อง (instruction) |
| `.rdata` | ข้อมูลอ่านอย่างเดียว |
| `.data` | ตัวแปร global/static ที่เขียนได้ ← **singleton pointers อยู่แถวนี้** |

ตัว exe เองและ DLL ทุกตัวที่ถูกโหลดเรียกว่า **module** แต่ละ module มี **base address** (จุดที่ถูก map เข้ามา)

### 3.2 RVA และสูตรที่ใช้ทุกวัน

**RVA (Relative Virtual Address)** = ระยะห่างจาก base ของ module

```
address จริง = module base + RVA
```

สิ่งที่ Cheat Engine เขียนว่า `"eldenring.exe"+03B16E30` แปลว่า: *เอา base ของ eldenring.exe มาบวก `0x3B16E30`*

> 📌 **Case File**
> ถ้า base = `0x140000000` (ค่ามาตรฐานที่ compiler ตั้งไว้ให้ exe 64 bit — และตรงกับ address ในโค้ด disassembly ของ 1.17.1 ที่ community อ้างอิง เช่น `0x1404fad46`) ตัวแปรของเราจะอยู่ที่ `0x140000000 + 0x3B16E30 = 0x143B16E30`
> แต่ tool **ไม่เดา base** — มันถาม OS ทุกครั้ง (`list_modules` → `main_mod.base`) เพราะ base อาจต่างออกไปได้

### 3.3 ทำไม RVA ถึง "คงที่" — และคงที่แค่ไหน

- ตัวแปร global ถูกกำหนดที่ตอน **compile/link** จึงอยู่ที่ RVA เดิมในไฟล์ exe ชุดเดียวกันเสมอ ไม่ว่าเปิดกี่ครั้ง
- **ASLR** (Address Space Layout Randomization) อาจย้าย *base* ทั้งก้อนไปที่อื่นในแต่ละรอบ แต่ RVA ไม่เปลี่ยน ("ทั้งตึกเลื่อนไปทั้งหลัง ห้องภายในยังห่างจากหน้าตึกเท่าเดิม")
- แต่พอ **เกมออก patch** ไฟล์ exe ถูก compile ใหม่ ตัวแปรย้ายที่ RVA เปลี่ยน → offset ทั้งหมดใน `offsets.json` ใช้ไม่ได้

จึงเป็นที่มาของ **version pinning** (spec §4.1): tool คำนวณ SHA-256 ของไฟล์ `eldenring.exe` แล้วหา profile ที่ key ตรงกัน ถ้าไม่มี → `UNSUPPORTED_VERSION` และไม่อ่านค่าใดๆ

> 📌 **Case File — ตัวเลขเวอร์ชันของคุณ**
> - แสดงในเกม (app ver.): `1.17.1`
> - `FileVersion` ของ exe: `2.7.1.0`
> - SHA-256: `1a3547101327f65d0c76da2f9190ac0aa66871ea42bae2aecc61e11a8b597891`
>
> เป็นการนับเวอร์ชัน "คนละระบบ" ของสิ่งเดียวกัน Hash คือตัวระบุที่แม่นที่สุด เพราะ byte เปลี่ยนนิดเดียว hash เปลี่ยนทั้งหมด

## บทที่ 4 — ข้อมูลเกมหน้าตาอย่างไรใน Memory

### 4.1 Struct, offset และ padding

โค้ดเกม (C++) จัดข้อมูลเป็น **struct/class** = กลุ่ม field เรียงต่อกันใน memory แต่ละ field มี **offset** = ระยะจากต้น struct

CPU ชอบให้ข้อมูลตั้งอยู่ที่ address ที่ "ลงตัวกับขนาด" (u32 ที่ address หาร 4 ลงตัว, pointer หาร 8 ลงตัว) compiler จึงแทรก **padding** ให้ นี่คือเหตุผลที่ offset มักเป็นเลขที่ดู "ข้าม" เช่น

```
struct SpecialEffectEntry (จาก eldenring crate ของ fromsoftware-rs):
  0x00  param_data        (pointer, 8 byte)
  0x08  param_id          (i32)                 ← "id" ใน profile ของเรา
  0x0C  _padc             (u32, padding)
  0x10  accumulator_info  (struct ขนาด 0x20)
  0x30  next              (pointer)             ← 0x10 + 0x20 = 0x30
  0x38  previous          (pointer)
  0x40  removal_timer     (f32)                 ← "timer" ใน profile ของเรา
  0x44  unk_removal_timer (f32)
  0x48  duration          (f32)                 ← "duration" ใน profile ของเรา
  0x4C  interval_timer    (f32)
  0x50  unk50             (0x28 byte)           → ขนาดรวม 0x78
```

🔬 **ระดับความมั่นใจ:**
`next = 0x30` ยืนยันจาก 2 แหล่ง (struct ใน crate และโค้ด disassembly ของ 1.17.1 `mov 0x30(%rcx),%rcx ; next = [entry + 0x30]` ที่ปรากฏใน PR ของ community) ส่วน `id`, `duration`, `removal_timer` ผ่านการ **พิสูจน์ด้วยเกมจริง** จาก log ของ `effects` (บทที่ 10) ฟิลด์ `unk…` ไม่รู้ความหมาย เราไม่แตะ

### 4.2 Pointer และ Pointer Chain

field ชนิด pointer เก็บ address ของ object อื่น การ **dereference** = "อ่านค่าที่ address นั้น" *Pointer chain* คือการ dereference ต่อกันหลายขั้น โดยแต่ละขั้นอาจบวก offset ก่อน

โน้ตที่ใช้ตลอดเล่ม: `[X]` = "ค่า 8 byte ที่อยู่ ณ address X"

เส้นทางของเรา (Path A ที่ Pointer Scan ให้มา):

```
p0 = [ eldenring.exe + 0x3B16E30 ]     ← ตัวแปร global (ตู้บัตรรายการ)
p1 = [ p0 + 0x0 ]                      ← PlayerIns
p2 = [ p1 + 0x580 ]                    ← PlayerGameData
runes = u32 ที่ p2 + 0x6C     level = u32 ที่ p2 + 0x68     attributes = 8×u32 ที่ p2 + 0x3C

และจาก p1 (PlayerIns) อีกสาย:
sp = [ p1 + 0x178 ]                    ← SpecialEffect
e  = [ sp + 0x8 ]                      ← entry แรกของ linked list
e' = [ e + 0x30 ]                      ← entry ถัดไป … จนกว่าจะเป็น 0
```

(ใน `offsets.json`: `world_chr_man_rva = 0x3B16E30`, `world_chr_man_to_player = 0x0`, `player_to_game_data = 0x580`, `player_to_sp_effect = 0x178`)

🔬 **ข้อควรรู้:** ชื่อฟิลด์ `world_chr_man_*` มาจากการที่ community มักเข้าถึง PlayerIns ผ่าน singleton ชื่อ `WorldChrMan` แต่ pointer ที่ Pointer Scan พบที่ `+0x3B16E30` **เราไม่ได้พิสูจน์ว่าเป็น `WorldChrMan` จริง** สิ่งเดียวที่พิสูจน์แล้วคือ "ตามเส้นทางนี้แล้วถึง PlayerIns/PlayerGameData ที่ค่าตรงกับเกม" ชื่อฟิลด์เป็นแค่ชื่อเรียกตาม spec

### 4.3 Linked list

ไม่รู้ล่วงหน้าว่าตอนนี้มี effect กี่ตัว จึงเก็บเป็น **linked list**: แต่ละ entry มี pointer `next` ไปหาตัวถัดไป ตัวสุดท้ายมี `next = 0`

```
SpecialEffect          entry A            entry B            entry C
 +0x8 head ─────────►  id=311100          id=1660000         id=26
                       next ────────────► next ────────────► next = 0  (จบ)
```

ข้อควรระวังตอนเดินรายการของโปรเซสอื่น (ซึ่งเกมกำลังแก้ไขอยู่ตลอด):

1. entry อาจถูกลบ/ย้ายระหว่างที่เราเดิน → pointer ชี้ที่ไม่มีข้อมูล
2. ถ้า offset ผิด รายการอาจ "วนเป็นวงกลม" หรือยาวไม่จบ

โค้ดจึงมีเกราะ 4 ชั้น (บทที่ 12): จำกัด 512 entry, ตรวจ pointer ซ้ำ (cycle), ตรวจว่าเป็น user-space pointer, และถ้าอ่านไม่ได้ก็ทิ้งทั้ง sample

### 4.4 vtable และ RTTI (รู้ไว้ตอนอ่านเอกสารของ community)

- object ของ C++ class ที่มี virtual function จะมี **vtable pointer** อยู่ที่ offset `0x0` (ชี้ไปตารางฟังก์ชัน) — ใน struct ข้างบน `SpecialEffect` เริ่มด้วย `vftable: usize` และ `head` จึงอยู่ที่ `0x8` ไม่ใช่ `0x0`
- **RTTI** (Run-Time Type Information) คือข้อมูลชื่อ class ที่ compiler ฝังไว้ในไฟล์ ทำให้นักวิจัยรู้ชื่อ `SpecialEffect`, `WorldChrMan`, `PlayerIns` — เอกสารของ crate ใส่หมายเหตุว่า "Source of name: RTTI"

### 4.5 สถาปัตยกรรมข้อมูลของเกมแบบหยาบๆ

```
ตัวแปร global (ใน exe)  ──►  "Manager" singleton (มีตัวเดียวทั้งเกม)
                                  └──►  entity: PlayerIns  (ตัวละครเรา)
                                           ├──►  PlayerGameData  (level, runes, stats …)
                                           └──►  SpecialEffect   (รายการ buff/debuff ที่ active)
```

รูปแบบ "ตัวแปร global → manager → entity → ข้อมูล" เป็นรูปแบบที่เจอในเกมส่วนใหญ่ เมื่อรู้แล้ว การ reverse engineer เกมอื่นก็ใช้วิธีคิดเดียวกัน

# Part II — โปรแกรมหนึ่งอ่านอีกโปรแกรมได้อย่างไร

## บทที่ 5 — Handle, OpenProcess, ReadProcessMemory

### 5.1 ภาพรวมของการอ่านข้าม process

เราอยู่ในโปรเซส Python แต่ข้อมูลอยู่ในโปรเซสเกม ต่างคนต่าง address space (บทที่ 2) จึงอ่านตรงๆ ไม่ได้ ต้องขอ **kernel ของ Windows ช่วยคัดลอก**:

```
Python (โปรเซสของเรา)                    Windows kernel                 eldenring.exe
────────────────────                    ──────────────                 ─────────────
1. OpenProcess(สิทธิ์, PID)  ─────────►  ตรวจสิทธิ์ ─► ให้ "handle"
2. ReadProcessMemory(handle,
     address, buffer, size)  ─────────►  ไปอ่าน virtual address นั้น ◄── (หน้าที่ map ไว้)
                             ◄─────────  คัดลอกลง buffer ของเรา
3. CloseHandle(handle)
```

**Handle** คือ "บัตรผ่าน" ที่ OS ออกให้ ระบุว่าเราได้สิทธิ์อะไรกับโปรเซสนั้น

### 5.2 สิทธิ์ขั้นต่ำ (หลัก least privilege)

```python
PROCESS_VM_READ                   = 0x0010   # อ่าน memory
PROCESS_QUERY_LIMITED_INFORMATION = 0x1000   # ถามสถานะ (เช่น ยังรันอยู่ไหม)
ACCESS_MASK = PROCESS_VM_READ | PROCESS_QUERY_LIMITED_INFORMATION   # = 0x1010
```

เรา **ไม่ขอ** สิทธิ์เขียน/จอง/สร้าง thread ในโปรเซสเกม จึงไม่มี "ทาง" ให้ tool แก้ไขเกมแม้โค้ดจะผิดพลาด นี่คือเหตุผลที่ spec §6 ระบุ *"Single OpenProcess call site; unit test asserts the flag mask"* และเทสต์ของเรา (`test_read_only_access_mask_and_no_write_apis`) ตรวจว่า `ACCESS_MASK == 0x1010` และ scan ซอร์สว่าไม่มีชื่อ API ที่เขียน memory

### 5.3 `ReadProcessMemory` ทำงานอย่างไร

```
BOOL ReadProcessMemory(HANDLE hProcess, LPCVOID lpBaseAddress,
                       LPVOID lpBuffer, SIZE_T nSize, SIZE_T *lpNumberOfBytesRead);
```

- อ่านช่วง `[address, address+size)` **ของโปรเซสเป้าหมาย** มาใส่ buffer ในโปรเซสเรา
- ถ้าบางส่วนของช่วงนั้นเข้าถึงไม่ได้ (ยังไม่ commit, ไม่มีสิทธิ์อ่าน) จะล้มเหลว หรืออ่านได้ไม่ครบ (error 299 `ERROR_PARTIAL_COPY`)
- คืนแค่ byte ดิบ — **ไม่รู้ว่ามันคืออะไร** ต้องแกะเองด้วย `struct.unpack`

โค้ดของเรา (ตัวจริง):

```python
def read(self, addr: int, size: int) -> bytes | None:
    """Exactly `size` bytes, or None on any failure (never zero-filled)."""
    if size <= 0 or not is_user_ptr(addr):
        return None
    buf = ctypes.create_string_buffer(size)
    n = ctypes.c_size_t(0)
    ok = _k32.ReadProcessMemory(self._h, ctypes.c_void_p(addr), buf, size, ctypes.byref(n))
    if not ok or n.value != size:
        return None
    return buf.raw
```

จุดสำคัญ: `if not ok or n.value != size: return None` = **อ่านไม่ครบถือว่าล้มเหลว** ไม่เคยเติม 0 (spec §4.5: อ่านไม่ครบ = "value unavailable" ไม่ใช่ศูนย์) ถ้าเรายอมคืนค่า `0` แทน "อ่านไม่ได้" runes จะกระพริบเป็น 0 ในบางจังหวะ ซึ่งเป็นบั๊กที่เจอบ่อยในเครื่องมือประเภทนี้

### 5.4 ข้อผิดพลาดที่เจอบ่อยและความหมาย

| อาการ | สาเหตุที่เป็นไปได้ | วิธีที่ tool จัดการ |
|---|---|---|
| `OpenProcess failed` (error 5, access denied) | โปรเซสถูกป้องกัน (เช่น EAC) หรือคนละสิทธิ์ผู้ใช้ | ตรวจ EAC ก่อนอยู่แล้ว; ไม่พยายามเลี่ยง |
| `ReadProcessMemory` คืนล้มเหลว | address ไม่ได้ map, หน้าถูก free ไปแล้ว, pointer ผิด | `read()` คืน `None` → ทิ้ง sample |
| อ่านได้แต่ค่าเป็นขยะ | offset ผิด หรือ layout เปลี่ยน | ตรวจช่วงค่า (level 1–713 ฯลฯ) → ทิ้ง sample พร้อม `last_error` |
| Handle เป็น 32 bit แล้ว crash | ลืมประกาศ `argtypes/restype` ใน ctypes | ประกาศครบทุกฟังก์ชัน (บทที่ 17) |
| อ่านไม่ได้เลยบน Python 32 bit | address เกิน 4 GiB | บังคับ Python 64 bit ตอนเริ่มโปรแกรม |

### 5.5 การอ่านไม่ใช่ "ภาพนิ่งแบบอะตอมมิก" (torn read)

เกมกำลังรันหลาย thread และแก้ข้อมูลตลอด เราอ่านทีละก้อน ไม่ได้ "หยุดเวลา" ดังนั้นอาจได้ข้อมูลที่ *ครึ่งเก่าครึ่งใหม่* (torn read) ได้ในทางทฤษฎี วิธีที่ tool ลดความเสี่ยง:

1. **อ่านเป็นก้อนเดียวต่อ entry:** entry ของ SpEffect อ่าน `0x38` byte ครั้งเดียว (แทนที่จะอ่านทีละ field) ช่วงเวลาที่ค่าจะเปลี่ยนกลางคันจึงสั้นลงมาก
2. **ตรวจความสมเหตุสมผลทุกค่า** ค่าเพี้ยนจะไม่ผ่านช่วง → ทิ้ง sample
3. **poll ซ้ำ 10 ครั้ง/วินาที** ค่าผิดๆ ชั่วขณะเดียวจึงถูกแทนด้วยค่าถูกในรอบถัดไป

## บทที่ 6 — Module Snapshot, Anti-Cheat และ Offline Launch

### 6.1 หา base address ของ exe

เราต้องรู้ base ของ `eldenring.exe` เพื่อบวก RVA ใช้ **Toolhelp snapshot**:

```
CreateToolhelp32Snapshot(TH32CS_SNAPMODULE | TH32CS_SNAPMODULE32, pid)
Module32FirstW / Module32NextW   → ไล่รายการ module (ชื่อ, base, path)
```

ข้อสังเกต: ตอนโปรเซสเพิ่งเริ่ม snapshot อาจล้มเหลวชั่วคราว (`ERROR_BAD_LENGTH`) tool จึง *retry* วนสูงสุด 60 วินาทีก่อนยอมแพ้ (`__main__.py` ขั้นตอนที่ 2) รายการ module ยังใช้ตรวจ EAC ด้วย (6.3)

### 6.2 EasyAntiCheat คืออะไร (ในระดับที่ต้องรู้)

**Anti-cheat** อย่าง EAC ทำงานคล้าย "ยามหน้าประตูเกม" — ป้องกันไม่ให้โปรแกรมภายนอกเข้ามาอ่าน/แก้ memory ของเกม เพราะการโกงในโหมดออนไลน์เริ่มต้นจากตรงนี้ โดยทั่วไปมันตรวจโปรเซสอื่น จำกัดการเปิด handle เข้าหาเกม และตรวจความสมบูรณ์ของไฟล์/memory

ผลต่อเรา: ถ้าเกมรันพร้อม EAC **การอ่าน memory จากภายนอกไม่ควรทำเลย** ไม่ใช่แค่ "อาจอ่านไม่ได้" แต่เป็นการเข้าใกล้สิ่งที่ระบบนี้ออกแบบมาเพื่อกัน

### 6.3 Offline launch: `-eac-nop-loaded`

Community รู้จักกันว่า การสั่ง `eldenring.exe -eac-nop-loaded` โดยตรง (ไม่ผ่าน launcher ที่โหลด EAC) จะรันเกมโดย **ไม่โหลด EAC** ซึ่งเป็นวิธีที่นักม็อดใช้ทดสอบแบบ offline แลกกับ *เล่นออนไลน์ไม่ได้*

tool ของเราใช้หลักนี้กับ 3 ชั้นป้องกัน:

| ชั้น | ทำอะไร | ที่ไหน |
|---|---|---|
| 1 | เปิดเกมด้วย flag นี้เอง (โหมดปกติของ `run`) | `game_launcher.launch()` |
| 2 | ก่อนอ่าน ตรวจรายการ module ว่ามีชื่อมี `easyanticheat` ไหม ถ้ามี → `EAC_ACTIVE` และ **หยุด** | `__main__.py` ขั้นตอนที่ 3 |
| 3 | ระหว่างรัน สแกน module ซ้ำทุก 2 วินาที ถ้า EAC โผล่มาทีหลัง → `EAC_DETECTED` และหยุด | ลูป poll |

โค้ดเปิดเกม (ตัวจริง):

```python
def launch(game_dir: Path) -> subprocess.Popen:
    env = dict(os.environ, SteamAppId=STEAM_APP_ID, SteamGameId=STEAM_APP_ID)
    return subprocess.Popen(
        [str(game_dir / GAME_EXE), "-eac-nop-loaded"], cwd=str(game_dir), env=env
    )
```

เราส่ง `SteamAppId` / `SteamGameId` ผ่าน **environment variable** ให้ Steam API เริ่มทำงานได้เมื่อรัน exe ตรงๆ **โดยไม่ต้องสร้างไฟล์ `steam_appid.txt` ในโฟลเดอร์เกม** (ตรงตามหลัก "ไม่แตะโฟลเดอร์เกม") 🔬 จากการรายงานของคุณ การเปิดเกมผ่าน tool ทำงานได้โดยไม่มีปัญหา ถ้าเครื่องอื่นมีปัญหา ให้ดู Appendix C

### 6.4 ขอบเขตและจริยธรรม (สำคัญ อ่านให้จบ)

⚠️ ผมไม่ใช่ทนายและไม่ใช่ตัวแทนของผู้พัฒนาเกม สิ่งที่บอกได้คือ **หลักที่โปรเจกต์นี้ยึด:**

1. **Offline เท่านั้น** ไม่เคยรันคู่กับ EAC และไม่ออกแบบให้ทำได้
2. **Read-only** ไม่มีโค้ดเขียน/แก้ค่าในเกม (การ "โกง" คือการแก้ค่า ซึ่งอยู่นอกขอบเขต)
3. **ข้อมูลไปที่ไฟล์ JSON ในเครื่อง** ไม่ส่งออกอินเทอร์เน็ต
4. "Read-only" **ไม่ได้แปลว่าปลอดภัยกับ anti-cheat เสมอไป** — ถ้าเผลอเปิดเกมแบบออนไลน์ (มี EAC) แล้วไปอ่านจากข้างนอก ความเสี่ยงของบัญชีเป็นของผู้ใช้ tool จึงถูกออกแบบให้ *ปฏิเสธ* กรณีนี้
5. ข้อกำหนดการใช้งานของเกมและกฎหมายท้องถิ่นเป็นเรื่องที่คุณต้องตรวจเอง

# Part III — Cheat Engine ทีละคลิก: เกิดอะไรขึ้นจริงๆ

## บทที่ 7 — First Scan และ Next Scan

### 7.1 เป้าหมาย

เรารู้ค่าที่เห็นบนจอ (เช่น runes = 10,089,063) แต่ไม่รู้ address เป้าหมายคือ **หาว่าค่านี้ถูกเก็บที่ address ไหนบ้าง** โดยวิธี "ไล่หาแพตเทิร์น byte ที่ตรงกับค่านั้นแล้วค่อยๆ กรอง"

### 7.2 First Scan ทำอะไรข้างใน

1. Cheat Engine เปิด handle เข้าโปรเซสเกม (คนละสิทธิ์กับ tool เรา: CE ทำงานแบบ Admin ตามหัวหน้าต่างของคุณ)
2. ถาม OS ว่าโปรเซสมี memory region อะไรบ้างและสิทธิ์อะไร (ผ่าน `VirtualQueryEx`)
3. เลือกเฉพาะ region ที่ตรงตามตัวเลือกใน *Memory Scan Options* (เช่น ติ๊ก **Writable**)
4. อ่านแต่ละ region มาทีละก้อน แล้วไล่ทุก address ที่ตรง **alignment 4** เทียบว่า 4 byte ตรงกับ `67 F2 99 00` (คือ 10,089,063 แบบ little-endian, บทที่ 1) ไหม
5. เก็บรายชื่อ address ที่ตรง

> 📌 **Case File**
> `Found: 7` — มี 7 address ที่เก็บเลข 10,089,063 อยู่พอดี:
> `7FF298462B78`, `7FF298C3F54C`, `7FF298C3F670`, `7FF298C3F674`, `7FF29FF880F0`, `7FF3A18DD264`, `7FF3A2CBE9DC`

ทำไมมีถึง 7 ที่ทั้งที่ runes มีค่าเดียว? เพราะเกมเก็บ/คัดลอกเลขนี้หลายที่ (ค่าสำหรับแสดง UI, บัฟเฟอร์ชั่วคราว, สำเนาในระบบอื่น) และบางที่อาจ *บังเอิญ* เป็นเลขเดียวกัน (เลข 4 byte ธรรมดาชนกันได้ง่ายในหน่วยความจำหลาย GB) เราไม่มีทางรู้จาก First Scan ครั้งเดียวว่าอันไหนของจริง

### 7.3 Next Scan: ตัวกรอง

หลักคิด: ค่าจริงของ runes ต้อง **เปลี่ยนตามเกม** ส่วนที่บังเอิญตรงหรือเป็นสำเนาที่ไม่อัปเดตจะไม่เปลี่ยนตาม

1. คุณเปลี่ยน runes ในเกม (ฆ่าศัตรู/ใช้จ่าย) → เลขใหม่ 10,273,265
2. **Next Scan** ไม่สแกนทั้งโปรเซสอีก แต่อ่านเฉพาะ 7 address เดิมมาเทียบกับเลขใหม่ → เก็บที่ตรง
3. ผลเหลือ **3** address: `7FF29FF880F0`, `7FF3A18DD264`, `7FF3A2CBE9DC` (ที่เหลือ 4 ตัวไม่เปลี่ยนตาม → ตัดทิ้ง)

คอลัมน์ในตาราง: *Value* = ค่าปัจจุบัน, *Previous* = ค่าตอน scan ก่อนหน้า, *First* = ค่าตอน First Scan (สีแดงแปลว่าเปลี่ยนไปจากตอนแรก)

### 7.4 ทำไมเหลือ 3 ตลอด ไม่ลดลงอีก

สามตัวนี้ "เปลี่ยนตามเกมจริง" ทั้งหมด (น่าจะเป็นตัวจริง + สำเนาที่ถูกอัปเดตพร้อมกัน) การ Next Scan ซ้ำจึงกรองต่อไม่ได้ ต้องใช้วิธีอื่น: **Pointer Scan** (บทที่ 8) เพราะเป้าหมายจริงของเราไม่ใช่ "หา address ที่ถูก" แต่คือ "หาเส้นทางที่ยั่งยืน" และเส้นทางที่ยั่งยืนเส้นเดียวที่ลงท้าย `…580 → 6C` ก็ตัดสินได้เองว่าตัวไหนคือตัวจริง

### 7.5 ทำไมผมเลือก `7FF3A2CBE9DC` (ฮิวริสติก ไม่ใช่การพิสูจน์)

ผมให้เหตุผลไว้ตอนนั้นว่า runes ควรอยู่ที่ `PlayerGameData + 0x6C` และ object บน heap มักเริ่มที่ address ลงตัว 16 ดังนั้น address ของ runes ควรลงท้าย hex ด้วย `C`

ตรวจกับตัวเลข: `0x7FF3A2CBE9DC − 0x6C = 0x7FF3A2CBE970` (ลงท้าย `0` = ลงตัว 16 ✔) ขณะที่ `…880F0` ลบ `0x6C` ได้ `…88084` (ลงตัวแค่ 4) และ `…DD264` ได้ `…DD1F8` (ลงตัวแค่ 8) ⚠️ นี่เป็นแค่ **ฮิวริสติกเพื่อเลือกตัวแรกที่จะลอง** ไม่ใช่หลักฐาน หลักฐานจริงคือผลของ Pointer Scan และการที่ tool อ่านค่าตรงกับเกม

## บทที่ 8 — Pointer Scan: เปลี่ยน address ชั่วคราวให้เป็นเส้นทางถาวร

### 8.1 ปัญหา

`7FF3A2CBE9DC` เป็น address บน **heap** ปิดเกมเปิดใหม่ก็ใช้ไม่ได้ (บทที่ 2) เราต้องการ *สูตร* ที่คำนวณ address นั้นได้ทุกครั้ง โดยเริ่มจากสิ่งที่คงที่ (`module + RVA`)

### 8.2 แนวคิดของอัลกอริทึม

ถ้า object ตั้งอยู่ที่ `T` แสดงว่า *ต้องมีใครสักคนใน memory ที่เก็บ pointer ชี้มาที่ (หรือใกล้ๆ) `T`* — ไม่งั้นโปรแกรมจะหา object นั้นไม่เจอ Pointer Scan จึงทำแบบ **ย้อนกลับ**:

```
เป้าหมาย T = 7FF3A2CBE9DC (runes)
ขั้น 1: หา "ทุกที่" ที่เก็บค่า X โดยที่  T − maxOffset ≤ X ≤ T
        (เช่น ที่เก็บ pointer ชี้ไป PlayerGameData เริ่มต้น ที่ T − 0x6C)
        → offset ที่ใช้ = T − X = 0x6C
ขั้น 2: สำหรับที่เก็บแต่ละตัวที่พบ ให้ทำซ้ำ: หา "ใครชี้มาหามัน"
        (ได้ที่ของ PlayerIns → offset 0x580, ต่อไป …)
… ทำต่อจนถึงระดับที่กำหนด (Max level) หรือจนพบที่เก็บที่เป็น "ตำแหน่งคงที่" ใน module
        (คือ address ที่อยู่ในช่วงของ eldenring.exe → เขียนเป็น module+RVA)
```

ขั้น "Generating pointermap" ที่คุณเห็น (แถบเขียว) คือการสร้างดัชนีของ *ทุกค่า 8 byte ในโปรเซสที่ดูเหมือน pointer* ไว้ล่วงหน้า เพื่อให้ค้นย้อนกลับได้เร็ว จึงกิน RAM และเวลามาก (ที่คุณรู้สึกว่า "คอมจะระเบิด")

### 8.3 อ่านหน้าต่างตั้งค่าที่คุณกรอก

| ตัวเลือก | ค่าที่ใช้ | ความหมาย |
|---|---|---|
| Maximum offset value | `200000` (ค่าเริ่มต้น 4095) | offset ต่อขั้นใหญ่สุดที่ยอมรับ (ทศนิยม) ตั้งสูงเพื่อไม่พลาด struct ที่ field อยู่ลึก |
| Max level | `4` | ลึกสุด 4 ขั้น (= จำนวน offset ในเส้นทาง) |
| Max different offsets per node | `3` | จำกัดจำนวน offset ต่างกันที่จะลองต่อ node เพื่อคุมไม่ให้ผลลัพธ์ระเบิด |
| Pointers must end with specific offsets | `6C` แล้ว `580` | บังคับให้ **ปลายทาง** เส้นทางลงท้ายด้วย `…, 580, 6C` (ลำดับที่ป้อน: offset สุดท้ายก่อน — ตรงกับป้าย "Last offset" ในหน้าจอ) |
| Max deviation | `0` | ตั้ง 0 เพื่อให้ offset ที่บังคับตรงเป๊ะ (ตามความเข้าใจจากการใช้งาน ไม่ได้ตรวจจากเอกสารของ CE) |

**ทำไม "บังคับลงท้าย `580, 6C`" ทำได้:** เพราะเรามีสมมติฐานล่วงหน้าจากความรู้ community ว่า runes อยู่ที่ `PlayerGameData+0x6C` และ `PlayerGameData` อยู่ที่ `PlayerIns+0x580` ข้อมูลนี้ตัดผลลัพธ์จากหลายล้านเส้นเหลือหยิบมือ ถ้าสมมติฐานผิด ผลลัพธ์จะเป็น 0 เส้น (และเราจะรู้ทันที — นี่เองคือ "การทดสอบสมมติฐาน" ที่ผมบอกไว้ตอนแนะนำ)

### 8.4 วิธีอ่านผลลัพธ์

ตารางที่ได้ (`Pointer paths: 2`):

| Base Address | Offset 0 | Offset 1 | Offset 2 | Offset 3 |
|---|---|---|---|---|
| `eldenring.exe+03B16E30` | 0 | 580 | 6C | |
| `eldenring.exe+03D66170` | 8 | 0 | 580 | 6C |

**สูตรการคำนวณของ Cheat Engine** (ตัวเลขทั้งหมด hex): เริ่มที่ `Base Address` แล้ว

```
p0 = [Base]                 ← dereference ที่ตำแหน่ง base
p1 = [p0 + Offset 0]        ← บวกก่อน แล้ว dereference
p2 = [p1 + Offset 1]
…
address ปลายทาง = p_last + Offset สุดท้าย    ← ขั้นสุดท้าย "ไม่ dereference"
```

**Path A** (3 offset: `0, 580, 6C`):

```
p0 = [eldenring.exe + 0x3B16E30]
p1 = [p0 + 0x0]          ← PlayerIns
p2 = [p1 + 0x580]        ← PlayerGameData
runes address = p2 + 0x6C
```

**Path B** (4 offset: `8, 0, 580, 6C`) มีขั้นเพิ่มอีกหนึ่งขั้น:

```
p0 = [eldenring.exe + 0x3D66170]
p1 = [p0 + 0x8]
p2 = [p1 + 0x0]
p3 = [p2 + 0x580]
runes address = p3 + 0x6C
```

ทั้งสองเส้นจบด้วย `+0x580 → +0x6C` เหมือนกัน แปลว่า **ทั้งคู่ไปถึง PlayerIns/PlayerGameData ตัวเดียวกันจาก "ประตูคงที่" คนละบาน** — คือมีตัวแปร global สองตัวที่ชี้เข้าไปหา object เดียวกันโดยอ้อม เราเลือก Path A เพราะสั้นกว่าและตรงกับโครงสร้างของ profile (3 ขั้น: `rva → +to_player → +to_game_data`)

### 8.5 ทำไม profile ของเราตรงกับ Path A

| ฟิลด์ใน `offsets.json` | ค่า | มาจาก |
|---|---|---|
| `world_chr_man_rva` | `0x3B16E30` | Base Address ของ Path A |
| `world_chr_man_to_player` | `0x0` | Offset 0 |
| `player_to_game_data` | `0x580` | Offset 1 |
| `game_data.runes` | `0x6C` | Offset 2 |

(`level = 0x68` และ `attributes = 0x3C` มาจาก layout ของ PlayerGameData ที่ community บันทึกไว้ แล้วพิสูจน์กับเกมจริงในบทที่ 9)

### 8.6 ทำไมไม่ทำ "Rescan" ตามตำราของ Cheat Engine

ขั้นตอนแบบตำรา: รีสตาร์ตเกม → หา runes address ใหม่ → **Rescan** ผลเดิมเพื่อกรองเส้นทางที่ยังใช้ได้ เพื่อตัดเส้นทางที่บังเอิญถูกแค่รอบเดียว

เราข้ามได้เพราะมีวิธีพิสูจน์ที่ *แรงกว่า*: ใส่เส้นทางลง profile แล้วให้ tool อ่านค่าออกมา 10 ค่า (level, runes, attributes 8 ตัว) เทียบกับเมนูในเกม ถ้าเส้นทางเป็นของ "บังเอิญ" ค่าทั้งสิบจะไม่ตรงพร้อมกัน (บทที่ 9) และยังทดสอบข้ามการเปิดเกมใหม่ด้วยการรันโหมด launch

## บทที่ 9 — จะรู้ได้อย่างไรว่า "ถูกจริง": บันไดหลักฐาน

คุณเขียนว่า *"อ่าน memory … ได้แบบ Absolutely Valid"* — ครึ่งหนึ่งถูก: **memory คือสถานะจริงที่เอนจินของเกมใช้** จึงเป็นแหล่งความจริงที่ดีที่สุด (ต่างจากการอ่านภาพหน้าจอที่ต้องเดา) แต่ค่าจะ "valid" **ต่อเมื่อเราชี้ถูกที่และแปลถูกชนิด** ไบต์ที่อ่านผิดที่ก็ยังเป็นไบต์ที่ "จริง" แค่ไม่ใช่ runes

### 9.1 บันไดหลักฐาน (Evidence Ladder)

| ขั้น | หลักฐาน | เราผ่านไหม | หมายเหตุ |
|---|---|---|---|
| L0 | ค่าอยู่ในช่วงที่เป็นไปได้ (level 1–713 ฯลฯ) | ✅ | จับ offset ผิดแบบโจ่งแจ้ง แต่ไม่พิสูจน์ว่าถูก |
| L1 | ค่าตรงกับที่เห็นในเมนูเกม | ✅ | level + runes + attributes 8 ตัว ตรงเป๊ะ |
| L2 | ค่า **ตามการเปลี่ยนแปลง** (เก็บ runes → `rune_delta` ขยับถูกทิศ) | ✅ | ตัดกรณี "บังเอิญค่าคงที่ตรง" |
| L3 | ยังถูกหลัง **เปิดเกมใหม่** | ✅* | *ตามที่คุณรายงานจากการรัน `run -v` |
| L4 | ถูกตลอดการเล่นยาว (loading, ตาย, fast travel, ออกเมนู) | ⏳ | V-06 ใน spec — ยังไม่ครบ |
| L5 | ถูกหลัง patch ใหม่ | ❌ (โดยธรรมชาติ) | build ใหม่ = ต้องทำใหม่ (บทที่ 17) |

### 9.2 ทำไม L1 แรงมาก

ถ้า offset ผิด ค่าที่อ่านได้ควรเป็นค่ากึ่งสุ่ม ความน่าจะเป็นที่ *ทั้ง 9 ค่า* (level + attributes 8 ตัว) จะตรงกับเกมพร้อมกันโดยบังเอิญ ประมาณ (1/99)⁹ ≈ 10⁻¹⁸ (ประมาณคร่าวๆ สมมติเป็นอิสระต่อกัน) — เล็กจนตัดความเป็นไปได้ที่จะ "บังเอิญ" ทิ้งได้ นี่คือเหตุผลที่ผมขอให้ "เทียบให้ตรงเป๊ะ" ไม่ใช่แค่ดูว่าขึ้น `[CONNECTED]`

⚠️ `[CONNECTED]` เพียงอย่างเดียวหมายถึง "ผ่านการตรวจช่วงค่า" (L0) เท่านั้น

### 9.3 ความเสี่ยงที่ยังเหลือ

- **Layout เปลี่ยนโดยไม่เปลี่ยน offset ต้นทาง** เช่น เกมเพิ่ม field กลางโครงสร้าง (ป้องกันด้วย hash pinning: patch ใหม่ = hash ใหม่ = ปฏิเสธ)
- **ค่าที่ตรงแต่ความหมายต่าง** เช่น "level" ที่แสดงกับที่เก็บอาจต่างกันในบางสถานะ (ตอนนี้ตรงหมด แต่ควรสังเกตในกรณีขอบ เช่น หลังใช้ของที่ปรับ stat ชั่วคราว)

## บทที่ 10 — ถอดรหัส SpEffect: จาก linked list ถึง JSON

### 10.1 SpEffect คืออะไร

เอนจินเก็บทุกอย่างที่ "มีผลชั่วคราวหรือถาวรต่อตัวละคร" เป็น **SpEffect** — buff จากสเปล (Golden Vow), ของใช้ (Gold-Pickled Fowl Foot), talisman ที่สวมอยู่, สถานะต่างๆ, รวมถึง effect ภายในของเอนจินที่ผู้เล่นไม่เห็น แต่ละตัวมี **ID** ชี้ไปที่แถวของตาราง `SpEffectParam` (ตาราง param ของเกม)

### 10.2 เริ่มจากความรู้ที่มี แล้วให้เกมยืนยัน

เราได้ layout ของ entry จากเอกสาร crate ของ community (บทที่ 4.1) ใส่เป็นค่าตั้งต้นใน profile แล้วสร้างคำสั่ง `effects` เพื่อ *ให้เกมบอกเราเอง* ว่า layout นั้นถูกไหม ผลจาก log แรกของคุณ:

- เดินรายการได้ครบ 12 entry โดยไม่ error → `player_to_sp_effect (0x178)`, `head (0x8)`, `next (0x30)` ถูก
- ID เป็นเลขสมเหตุสมผล (26, 1922, 100620, 310210 …) → `id (0x8)` ถูก
- ค่า `-1.00` (ถาวร) และค่าสั้นๆ เช่น `1.50`, `0.10` → `duration (0x48)` ถูก

### 10.3 การทดลอง: ทำสิ่งหนึ่ง สังเกตสิ่งที่เปลี่ยน (differential observation)

หลักเดียวกับ Next Scan คือ **ก่อสร้างความรู้จากความต่าง** คุณทำทีละอย่างแล้วดูแถว `+`/`-`:

| ทำอะไรในเกม | สิ่งที่โผล่/หาย | ตีความ |
|---|---|---|
| ถอด/ใส่ Gold Scarab | `311100 │ -1.00 │ -1.00` หาย/กลับมา | effect **ถาวร** ผูกกับ talisman → `passive` |
| ใช้ Gold-Pickled Fowl Foot | `3971 │ 180.00 │ 179.60` | buff **มีเวลา** 180 วินาที → `active` |
| ร่าย Flame, Grant Me Strength | `1605000 │ 30.00 │ 29.93` + `1605001`, `1605002` (0.10) | buff 30 วินาที + effect ช่วยสั้นๆ |
| ร่าย Golden Vow | `1660000 │ 80.00 │ 79.77` + `1660001`, `1660002` (0.10) | buff 80 วินาที |

### 10.4 พิสูจน์ความหมายของ timer

ดู `1605000` ตลอดหลายช่วง: `30.00 → 29.82 → 29.65 …` และอีกครั้งเห็น `8.28` ระหว่างทาง จากนั้น effect หายไปพร้อม `…001`/`…002` — **timer นับลงจาก duration ไปหา 0** ดังนั้น `removal_timer` = "เวลาที่เหลือ" → `timer_mode: "remaining"` (ถ้าเป็นแบบนับขึ้น ค่าต้องเริ่มที่ 0 ไม่ใช่ 30)

### 10.5 เสียงรบกวน (noise) ที่ต้องรู้จัก

| ประเภท | ตัวอย่าง | พฤติกรรม | วิธีจัดการ |
|---|---|---|---|
| effect ภายในสั้นมาก | `45`, `133`, `100000`, `100001`, `102368` | duration `0.00`–`0.10` โผล่/หายทุกเฟรม | ไม่ใส่ใน `effects.json` (ข้ามอัตโนมัติ) หรือซ่อนด้วย `effects -q` |
| effect ผู้ช่วยของ buff | `1605001/2`, `1660001/2` | 0.10 วินาที ควบคู่กับ buff หลัก | ไม่ต้องใส่ |
| effect ที่ต่ออายุตลอด | `4600`/`4601` | duration 30 แต่ timer ค้างที่ 30.00 | **ห้ามใส่ใน `active`** (ไม่ใช่ buff ที่นับถอยหลังจริง) |
| effect ถาวรที่ไม่ใช่ของที่เรารู้ | `26`, `1922`, `310210`, `320500`, `350200` | `-1.00 │ -1.00` | ปล่อยไว้ก่อน จนรู้ว่าเป็นของอะไร |

🔬 ยังไม่ทราบสาเหตุที่แท้จริงของ `4600/4601` (ค้างที่ 30.00 สลับ ID สองตัว) ตั้งสมมติฐานว่าเป็นสถานะที่ถูกรีเซ็ตต่อเนื่อง แต่ยังไม่ได้พิสูจน์ (Appendix E)

### 10.6 กฎการจัดประเภทใน `effects.json`

โค้ด `_classify` ทำตามลำดับ (spec §4.4):

1. ID อยู่ใน `passive` → รายงานเป็น `passive_buffs` (ไม่สน timer)
2. ID อยู่ใน `active` → ต้องมี `duration > 0`, ค่าจำกัด (ไม่ใช่ NaN/inf) และ `remaining > 0` (และไม่เกิน `duration + 1`) ถึงจะรายงาน
3. นอกนั้นนับใน `ignored_effects`

**คำนวณเวลาเริ่ม (activation)** จาก `now − (duration − remaining)` ตัวอย่างจริงจาก JSON ของคุณ (timestamp `03:27:23.350Z`):

| buff | duration | remaining | ผ่านไปแล้ว | เวลาเริ่มที่คำนวณได้ |
|---|---|---|---|---|
| Flame! Grant Me Strength | 30.0 | 21.84 | 8.16 s | ≈ `03:27:15.19` ✔ (JSON: `…15.191`) |
| Golden Vow | 80.0 | 76.04 | 3.96 s | ≈ `03:27:19.39` ✔ (JSON: `…19.391`) |

(ต่างที่หลักมิลลิวินาทีเพราะ `remaining` ถูกปัดเศษก่อนแสดง) ผลคือเวลาเริ่มถูกต้องแม้ tool เปิดทีหลังใช้ buff เพราะคำนวณจากค่าที่เหลือ ไม่ใช่จากตอนที่ tool "เห็น" ครั้งแรก

## บทที่ 12 — ทัวร์โค้ด

### 12.1 `memory_reader.py`: ชั้นล่างสุด

ตัวช่วยที่ทำงานกับ "อะไรก็ตามที่มี `.read(addr, size)`" (ทั้งของจริงและ fake ในเทสต์):

```python
def read_ptr(mem, addr: int) -> int | None:
    b = mem.read(addr, 8)
    return None if b is None else struct.unpack("<Q", b)[0]
```

`struct.unpack("<Q", b)` แปลง 8 byte เป็นเลข u64 แบบ little-endian ส่วน `read()` ของจริงดูในบทที่ 5.3

⚠️ **ทำไมต้องประกาศ `argtypes`/`restype`:** `ctypes` โดยปริยายถือว่าฟังก์ชัน C คืน `int` 32 bit ถ้าไม่ประกาศ `HANDLE`/pointer 64 bit จะถูกตัดครึ่ง → handle เพี้ยน/crash เป็นบั๊กคลาสสิกของการเรียก WinAPI ผ่าน Python (ดูโค้ดส่วน `if IS_WINDOWS:` ใน `memory_reader.py`)

### 12.2 `Sampler`: หัวใจ

ตัวช่วยเดินหนึ่งขั้น: อ่าน pointer แล้วแยกกรณี "อ่านไม่ได้ / เป็น null / ไม่ใช่ pointer จริง":

```python
def _follow(self, addr: int, name: str) -> tuple[int | None, Sample | None]:
    v = read_ptr(self.mem, addr)
    if v is None:
        return None, self._wait(f"read failed: {name}")
    if v == 0:
        return None, self._wait()  # normal on title screen / loading
    if not is_user_ptr(v):
        return None, self._wait(f"invalid pointer {name}=0x{v:X}")
    return v, None
```

ข้อสังเกต: **null ไม่ใช่ error** (`return None, self._wait()` ไม่มีข้อความ) เพราะตอนอยู่หน้า title หรือกำลังโหลด pointer เป็น null ตามปกติ ส่วน "อ่านไม่ได้" หรือ "ไม่ใช่ pointer จริง" เป็นสัญญาณผิดปกติ จึงใส่ `error` ให้ `-v` แสดง

ฟังก์ชันหลัก:

```python
def sample(self, now: datetime | None = None) -> Sample:
    now = now or datetime.now(timezone.utc)
    p = self.profile

    wcm, w = self._follow(self.base + p.world_chr_man_rva, "WorldChrMan")
    if w is not None:
        return w
    player, w = self._follow(wcm + p.world_chr_man_to_player, "PlayerIns")
    if w is not None:
        return w
    gd, w = self._follow(player + p.player_to_game_data, "PlayerGameData")
    if w is not None:
        return w

    level = read_u32(self.mem, gd + p.level)
    runes = read_u32(self.mem, gd + p.runes)
    raw = self.mem.read(gd + p.attributes, 32)
    if level is None or runes is None or raw is None:
        return self._wait("read failed: PlayerGameData fields")
    attrs = struct.unpack("<8I", raw)

    if not LEVEL_RANGE[0] <= level <= LEVEL_RANGE[1]:
        return self._wait(f"level={level} outside {LEVEL_RANGE} (PlayerGameData+0x{p.level:X})")
    if runes > RUNES_MAX:
        return self._wait(f"runes={runes} outside 0..{RUNES_MAX} (PlayerGameData+0x{p.runes:X})")
    for name, v in zip(ATTR_NAMES, attrs):
        if not ATTR_RANGE[0] <= v <= ATTR_RANGE[1]:
            return self._wait(f"{name}={v} outside {ATTR_RANGE} (PlayerGameData+0x{p.attributes:X})")

    active: list[dict] = []
    passive: list[dict] = []
    ignored = 0
    if p.sp_effect is not None:
        entries, err = self._read_effect_list(player)
        if err is not None:
            return self._wait(err)
        active, passive, ignored = self._classify(entries, now)

    if self.session_start_runes is None:
        self.session_start_runes = runes
    character = {
        "level": level,
        "runes": runes,
        "attributes": dict(zip(ATTR_NAMES, attrs)),
        "active_buffs": active,
        "passive_buffs": passive,
    }
    return Sample("CONNECTED", character, ignored, None, runes)
```

ลำดับเหตุการณ์: เดิน 3 ขั้น (`WorldChrMan → PlayerIns → PlayerGameData`) → อ่านฟิลด์ → **ตรวจช่วงค่า** → (ถ้า profile รองรับ) อ่านและจัดประเภท buff → ตั้ง `session_start_runes` ครั้งแรก → ส่งผล ทุกจุดที่ผิดปกติ `return self._wait(...)` คือ "ทิ้งทั้ง sample" (correct-or-silent)

### 12.3 เดิน linked list อย่างระวัง

```python
def _read_effect_list(self, player: int):
    lay = self.profile.sp_effect
    e = lay.entry
    sp = read_ptr(self.mem, player + lay.player_to_sp_effect)
    if sp is None:
        return None, "read failed: SpecialEffect pointer"
    if sp == 0:
        return [], None
    if not is_user_ptr(sp):
        return None, f"invalid pointer SpecialEffect=0x{sp:X}"
    cur = read_ptr(self.mem, sp + lay.head)
    if cur is None:
        return None, "read failed: SpEffect list head"

    span = max(e.id, e.next, e.duration, e.timer) + 8
    seen: set[int] = set()
    out: list[tuple[int, float, float]] = []
    while cur != 0:
        if len(out) >= MAX_EFFECTS:
            return None, f"SpEffect list longer than {MAX_EFFECTS} entries"
        if cur in seen:
            return None, "cycle in SpEffect list"
        if not is_user_ptr(cur):
            return None, f"invalid SpEffect entry pointer 0x{cur:X}"
        seen.add(cur)
        blob = self.mem.read(cur, span)
        if blob is None:
            return None, f"read failed: SpEffect entry 0x{cur:X}"
        eid = struct.unpack_from("<I", blob, e.id)[0]
        nxt = struct.unpack_from("<Q", blob, e.next)[0]
        dur = struct.unpack_from("<f", blob, e.duration)[0]
        timer = struct.unpack_from("<f", blob, e.timer)[0]
        out.append((eid, dur, timer))
        cur = nxt
    return out, None
```

ชั้นป้องกัน (เรียงตามที่เห็นในโค้ด): เกิน `MAX_EFFECTS` (512), pointer ซ้ำ (cycle), ไม่ใช่ user-space pointer, อ่านไม่ได้ และ `span = max(offset ทั้งหมด) + 8` คืออ่าน entry เป็นก้อนเดียว (บทที่ 5.5) แล้วใช้ `struct.unpack_from` แกะ field ตาม offset ใน profile

### 12.4 จัดประเภท buff

```python
def _classify(self, entries, now: datetime):
    mode = self.profile.sp_effect.entry.timer_mode
    passive: dict[int, dict] = {}
    active: dict[int, dict] = {}
    ignored = 0
    for eid, dur, timer in entries:
        pe = self.effects.passive.get(eid)
        if pe is not None:
            passive.setdefault(eid, {
                "id": eid, "name": pe.name, "category": pe.category, "source_name": pe.source_name,
            })
            continue
        ae = self.effects.active.get(eid)
        if ae is None or not (math.isfinite(dur) and math.isfinite(timer)) or dur <= 0:
            ignored += 1
            continue
        remaining = timer if mode == "remaining" else dur - timer
        if remaining <= 0 or remaining > dur + 1.0:
            ignored += 1
            continue
        prev = active.get(eid)
        if prev is None or remaining > prev["remaining_seconds"]:
            active[eid] = {
                "id": eid,
                "name": ae.name,
                "remaining_seconds": round(remaining, 2),
                "max_duration_seconds": round(dur, 2),
                "activation_timestamp_iso": iso(now - timedelta(seconds=dur - remaining)),
            }
    return list(active.values()), list(passive.values()), ignored
```

จุดควรสังเกต:
- **passive ตรวจก่อน active** → effect ถาวรถูกรายงานโดยไม่ดู timer
- `remaining > dur + 1.0` = ค่านับเวลาผิดปกติ (เช่น ตั้ง `timer_mode` ผิด) → ทิ้ง ไม่รายงานตัวเลขที่ไม่สมเหตุสมผล
- ถ้ามี entry ID เดียวกันสองตัว เก็บตัวที่เหลือเวลามากกว่า

### 12.5 `json_logger.py`: เขียนไฟล์ไม่ให้ผู้อ่านเห็นไฟล์ครึ่งเดียว

```python
def write(self, doc: dict) -> bool:
    self._tmp.write_text(json.dumps(doc, indent=2), encoding="utf-8")
    for _ in range(5):
        try:
            os.replace(self._tmp, self.path)
            return True
        except PermissionError:  # a reader has the file open
            time.sleep(0.02)
    return False
```

เขียนลงไฟล์ชั่วคราวก่อน แล้ว `os.replace` (การสลับชื่อไฟล์เป็นการกระทำเดียวที่ OS ทำแบบ atomic) ผู้อ่านจึงเห็นแต่ไฟล์เก่าเต็มไฟล์ หรือไฟล์ใหม่เต็มไฟล์เสมอ ไม่เคยเห็นไฟล์ที่เขียนค้างครึ่ง ถ้าผู้อ่านเปิดไฟล์ค้างไว้บน Windows (`PermissionError`) จะ retry 5 ครั้ง ห่างกัน 20 ms

### 13.1 หลัก 5 ข้อ

| หลัก | ความหมาย | ตัวอย่างในโปรเจกต์ |

### 13.2 ทำไมทดสอบด้วย "memory ปลอม"

เราทดสอบตรรกะทั้งหมดโดยไม่ต้องมีเกม ด้วยคลาส `FakeMem` ที่มี `.read(addr, size)` เหมือนของจริง แต่อ่านจากดิกชันนารีที่เราสร้างเอง (วาง pointer chain, ค่า level/runes และ linked list ลงไป) จึงทดสอบได้เช่น:

- เดินได้ถูกทั้งโหมด `remaining`/`elapsed`
- null → รอเงียบๆ ไม่มี error
- ค่าออกนอกช่วง → ทิ้งพร้อมข้อความ
- linked list วนเป็นวงกลม / ยาวเกิน 512 / pointer เพี้ยน → ทิ้ง
- JSON ทุกสถานะ validate ผ่าน schema

**ข้อจำกัดที่ต้องรู้:** เทสต์เหล่านี้พิสูจน์ *ตรรกะของเรา* ไม่ได้พิสูจน์ *ชั้น WinAPI* (`OpenProcess`, `ReadProcessMemory`, ...) หรือ *ความถูกต้องของ offset* — สองอย่างหลังพิสูจน์ได้เฉพาะกับเกมจริง ซึ่งเราทำแล้ว (บทที่ 9–10)

### 13.3 ทำไม tool ไม่ควรกินเครื่อง (เรื่องพัดลมที่คุณถาม)

ต่อรอบ poll tool อ่านประมาณ 6 ครั้งสำหรับ chain+stats และอีกครั้งละ 1 entry (ปกติสิบกว่าตัว) แต่ละครั้งใช้เวลาระดับไมโครวินาที บวกเขียนไฟล์เล็กๆ 10 ครั้ง/วินาที ภาระ CPU น้อยมาก พัดลมดังขึ้นมักมาจากตัวเกมและ Cheat Engine (โดยเฉพาะที่ค้าง pointermap หรือรายการสแกนไว้) ถ้าสงสัยให้ดูใน Task Manager หรือลด `--hz`

# Part V — Advanced

## บทที่ 15 — Signature (AOB) Scanning: ให้ Tool หา Offset เองหลัง Patch

### 15.1 ปัญหา

ตอนนี้ทุก patch ต้องทำ Pointer Scan ใหม่ด้วยมือ วิธีอัตโนมัติที่ community นิยมคือ **AOB (Array Of Bytes) / signature scan**: แทนที่จะจำ "RVA ของตัวแปร" (เปลี่ยนทุก build) ให้จำ **"หน้าตาของโค้ด" ที่อ้างถึงตัวแปรนั้น** เพราะโค้ดชุดเดิมมักมี byte เหมือนเดิมแม้ที่อยู่ตัวแปรจะย้าย

### 15.2 กลไก

โค้ด x86-64 ที่อ่านตัวแปร global มักใช้ **RIP-relative addressing**: instruction เก็บ "ระยะห่างจาก instruction ถัดไป" ไว้ใน 4 byte (`disp32` แบบมีเครื่องหมาย) ไม่ได้เก็บ address ตรงๆ

ตัวอย่าง `mov rax, [rip+disp32]` แปลงเป็น byte: `48 8B 05 <disp32>` (ยาว 7 byte)

```
target = (address ของ instruction ถัดไป) + disp32
       = address_of_instr + 7 + disp32
```

กระบวนการ:

1. สแกนส่วน `.text` ของ module หาแพตเทิร์น เช่น `48 8B 05 ?? ?? ?? ?? 48 85 C0 74 0F` (`??` = byte อะไรก็ได้ เพราะ `disp32` เปลี่ยนตาม build)
2. ตรวจว่า **เจอพอดี 1 ที่** (0 หรือ >1 = ใช้ไม่ได้ ต้องปรับแพตเทิร์น)
3. อ่าน `disp32` แล้วคำนวณ RVA ของตัวแปรตามสูตรข้างบน

### 15.3 โค้ดทดลอง (รันได้และผ่านการทดสอบ)

ตัวอย่างนี้ใช้ **image ปลอม** ที่ผมประกอบเอง โดยเลือกตัวเลขให้ instruction ชี้ไปที่ RVA `0x3B16E30` เท่ากับใน profile ของคุณ เพื่อให้เห็นภาพ ⚠️ **นี่ไม่ใช่แพตเทิร์นจริงของ Elden Ring** และผมไม่ได้อ้างว่าแพตเทิร์นนี้มีอยู่จริงในเกม

```python
"""Lab 5: signature (AOB) scan + RIP-relative resolution on a SYNTHETIC image.

The numbers are made up so that the instruction resolves to RVA 0x3B16E30
(the real profile value). No real Elden Ring pattern is claimed here.
"""
import re
import struct


def compile_aob(pattern: str) -> re.Pattern:
    """'48 8B 05 ?? ?? ?? ??' -> compiled byte regex ('??' = any byte)."""
    parts = []
    for tok in pattern.split():
        parts.append(b"." if tok in ("??", "?") else re.escape(bytes([int(tok, 16)])))
    return re.compile(b"".join(parts), re.DOTALL)


def resolve_rip_relative(image: bytes, match_off: int, disp_off: int, instr_len: int) -> int:
    """Target RVA of an instruction like `mov rax, [rip+disp32]`.

    target = (address of NEXT instruction) + signed disp32
           = match_off + instr_len + disp32          (all as RVAs)
    """
    disp = struct.unpack_from("<i", image, match_off + disp_off)[0]
    return match_off + instr_len + disp


def find_unique(image: bytes, pattern: str) -> int:
    hits = [m.start() for m in compile_aob(pattern).finditer(image)]
    if len(hits) != 1:
        raise LookupError(f"pattern matched {len(hits)} times (need exactly 1)")
    return hits[0]


if __name__ == "__main__":
    INSTR_RVA, TARGET_RVA = 0x1A2B3C0, 0x3B16E30
    image = bytearray(0x1A2B500)                       # fake .text, all zeros
    disp = TARGET_RVA - (INSTR_RVA + 7)                # 7 = length of `48 8B 05 <disp32>`
    # mov rax,[rip+disp32] ; test rax,rax ; jz +0F   (a plausible "singleton check" shape)
    code = bytes([0x48, 0x8B, 0x05]) + struct.pack("<i", disp) + bytes([0x48, 0x85, 0xC0, 0x74, 0x0F])
    image[INSTR_RVA:INSTR_RVA + len(code)] = code

    at = find_unique(bytes(image), "48 8B 05 ?? ?? ?? ?? 48 85 C0 74 0F")
    rva = resolve_rip_relative(bytes(image), at, disp_off=3, instr_len=7)
    print(f"pattern found at RVA 0x{at:X}; disp32 = 0x{disp:X}; resolved RVA = 0x{rva:X}")
    assert at == INSTR_RVA and rva == TARGET_RVA
    print("OK")
```

ผลรัน: `pattern found at RVA 0x1A2B3C0; disp32 = 0x20EBA69; resolved RVA = 0x3B16E30`

### 15.4 ข้อจำกัดของ AOB

- แพตเทิร์นที่ดีต้อง **เจอที่เดียว** และ **ทนต่อ patch** — ต้องลองหลาย build จึงรู้ว่าทนแค่ไหน
- compiler ที่เปลี่ยนชุดคำสั่ง (เลือก register ต่างกัน) ทำให้แพตเทิร์นพังได้
- ช่วยได้เฉพาะ *จุดเริ่ม* (RVA ของ root) ส่วน offset ภายใน struct (`0x580`, `0x6C`, …) ยังต้องยืนยันเอง เพราะเกมอาจจัด layout ใหม่
- โปรเจกต์นี้ **ยังไม่ทำ** AOB (ตรงกับ "out of scope" ใน spec §8) ถ้าจะทำ ควรออกแบบให้ตัวสแกน *ตรวจผลด้วยกฎ L0–L1* (บทที่ 9) ก่อนเชื่อผลเสมอ

## บทที่ 17 — รอดจาก Patch, ประสิทธิภาพ, กับดักของ ctypes

### 17.1 ทุก patch เกิดอะไรขึ้น

| สิ่งที่อาจเปลี่ยน | ผลต่อเรา | สัญญาณ |
|---|---|---|
| RVA ของตัวแปร global | `world_chr_man_rva` ผิด | hash เปลี่ยน → `UNSUPPORTED_VERSION` (ปลอดภัย) |
| offset ระหว่าง object | เส้นทางเสีย | หลังเพิ่ม profile ใหม่ ต้องยืนยันด้วยบันไดหลักฐาน |
| layout ของ struct | field เลื่อน | ค่าออกนอกช่วง หรือค่าไม่ตรงเมนู (L1 ล้ม) |
| SpEffect ID/ความหมาย | ตาราง `effects.json` เพี้ยน | buff ชื่อผิด (ตรวจด้วย `effects` ซ้ำ) |

**ขั้นตอนหลัง patch (ครั้งแรกใช้เวลานาน ครั้งต่อๆ ไปเร็วขึ้นมาก):**

1. `python -m elden_telemetry hash` → hash ใหม่
2. เปิดเกม offline → Cheat Engine: First/Next Scan runes → Pointer Scan (ลงท้าย `580, 6C` ถ้ายังใช้ได้) → ได้ `world_chr_man_rva` + `world_chr_man_to_player` ใหม่
3. **เพิ่ม profile ใหม่ตาม hash ใหม่** (อย่าทับของเก่า)
4. `run --attach -v` แล้วเทียบ level/runes/attributes (L1–L2)
5. `effects -q` ตรวจ layout SpEffect (ถ้า error แสดงว่า offset ตัวใดตัวหนึ่งขยับ) และเช็กว่า ID ใน `effects.json` ยังตรงกับของที่ใช้จริง

### 17.2 ประสิทธิภาพ

ต้นทุนหลักคือจำนวนครั้งที่เรียก `ReadProcessMemory` (แต่ละครั้งเข้า kernel) การอ่านทั้ง entry เป็นก้อนเดียว (แทนทีละ field) ลดจำนวนครั้งลงหลายเท่า และ 10 Hz เพียงพอสำหรับข้อมูลที่เปลี่ยนช้ากว่านั้น (`--hz` ปรับได้ 1–30)

### 17.3 กับดักของ `ctypes` ที่เจอบ่อย

| กับดัก | อาการ | วิธีแก้ในโปรเจกต์ |
|---|---|---|
| ไม่ประกาศ `restype`/`argtypes` | handle/pointer 64 bit ถูกตัดเหลือ 32 bit | ประกาศครบ |
| ใช้ `c_int` แทน `c_void_p` กับ address | address สูงล้น | ใช้ `c_void_p` |

| ใช้ Python 32 bit | อ่านเป้าหมาย 64 bit ไม่ได้ | ตรวจ `struct.calcsize("P") == 8` |
| ใช้ `wintypes.HANDLE` เทียบ `INVALID_HANDLE_VALUE` | ค่าเทียบผิดชนิด | เทียบเป็น int ที่ `c_void_p(-1).value` |

## Lab 3 — เกมจำลอง: เดิน pointer chain ด้วยโค้ดของเราเอง (30 นาที, Windows)

**เป้าหมาย:** เห็น (1) ว่า address ของ object เปลี่ยนทุกรอบ (2) ว่าโค้ด `ProcessMemory` + `read_ptr` เดินเส้นทางเดียวกับที่เราใช้กับเกมจริงได้ โครงสร้างเลียนแบบของจริง: `ROOT → +0 → PlayerIns → +0x580 → PlayerGameData → +0x68/+0x6C`

**`labs\toy_game.py`** (สร้าง object จำลอง แล้วบวก runes ทีละ 100 ทุกวินาที):

```python
"""Toy 'game' for Lab 3: builds Manager -> PlayerIns -> PlayerGameData in memory.

Run it, note the printed PID and ROOT address, then read it from another process
with labs/toy_reader.py. Every run prints DIFFERENT addresses for the heap objects.
"""
import ctypes
import os
import time


class PlayerGameData(ctypes.Structure):
    _fields_ = [("pad0", ctypes.c_uint8 * 0x68), ("level", ctypes.c_uint32), ("runes", ctypes.c_uint32)]


class PlayerIns(ctypes.Structure):
    _fields_ = [("pad0", ctypes.c_uint8 * 0x580), ("game_data", ctypes.c_void_p)]


class Manager(ctypes.Structure):
    _fields_ = [("player", ctypes.c_void_p)]  # offset 0 -> PlayerIns


gd = PlayerGameData()
gd.level, gd.runes = 42, 1000
player = PlayerIns()
player.game_data = ctypes.addressof(gd)
manager = Manager()
manager.player = ctypes.addressof(player)

# ROOT plays the role of "eldenring.exe + RVA": a fixed place that holds a pointer.
root = ctypes.c_void_p(ctypes.addressof(manager))

if __name__ == "__main__":
    print(f"PID  = {os.getpid()}")
    print(f"ROOT = 0x{ctypes.addressof(root):X}   (holds a pointer to Manager)")
    print(f"(spoiler) PlayerIns at 0x{ctypes.addressof(player):X}, PlayerGameData at 0x{ctypes.addressof(gd):X}")
    while True:
        gd.runes += 100
        time.sleep(1)
```

**`labs\toy_reader.py`** (ใช้ `ProcessMemory` ของโปรเจกต์อ่านจากอีกโปรเซส):

```python
"""Lab 3 reader: walks ROOT -> +0 -> +0x580 -> (+0x68 level, +0x6C runes) using the project's own code.

Usage (Windows, 64-bit Python, from the folder that contains elden_telemetry/):
    python labs/toy_reader.py <PID> <ROOT hex>
"""
import sys
import time
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parent.parent))  # project root

from elden_telemetry.memory_reader import ProcessMemory, is_user_ptr, read_ptr, read_u32

pid, root = int(sys.argv[1]), int(sys.argv[2], 16)
mem = ProcessMemory(pid)
try:
    while mem.alive():
        manager = read_ptr(mem, root)                 # [ROOT]
        player = read_ptr(mem, manager + 0x0) if manager and is_user_ptr(manager) else None
        gd = read_ptr(mem, player + 0x580) if player and is_user_ptr(player) else None
        if gd and is_user_ptr(gd):
            print(f"level={read_u32(mem, gd + 0x68)} runes={read_u32(mem, gd + 0x6C)}")
        else:
            print("chain not resolvable")
        time.sleep(1)
finally:
    mem.close()
```

**ขั้นตอน**

1. เทอร์มินัล A: `python labs\toy_game.py` → จดค่า `PID` และ `ROOT`
2. เทอร์มินัล B (ที่โฟลเดอร์โปรเจกต์): `python labs\toy_reader.py <PID> <ROOT ที่จด>` → ควรเห็น `level=42 runes=…` เพิ่มทีละ 100
3. กด Ctrl+C ทั้งสอง แล้วรัน A ใหม่ → **ดู PlayerIns/PlayerGameData ที่พิมพ์ออกมา: address เปลี่ยน** (นี่คือ heap ที่จองใหม่)
4. อ่านด้วย Cheat Engine: attach `python.exe` ของ A, สแกนหา runes, ทำ Pointer Scan (ลงท้าย `580, 6C`) แล้วเทียบกับสิ่งที่โค้ดรู้อยู่แล้ว

⚠️ ข้อแตกต่างจากเกมจริง: ที่นี่ `ROOT` เป็นตัวแปรใน Python จึงเปลี่ยนที่ทุกรอบ (ไม่มี "module + RVA" ที่คงที่แบบ exe ที่ compile แล้ว) เพื่อให้เห็นภาพ "ตู้บัตร → บัตร → ห้อง" ในเกมจริงตู้บัตรจะอยู่ที่ RVA เดิม
🔬 ผมตรวจตรรกะเดินเส้นทางของ Lab นี้ด้วยการรันในโปรเซสเดียวบน Linux (ตัวเลข `42`/`1000` ออกถูกต้อง) แต่ชั้น Windows (`ProcessMemory`) ต้องลองบนเครื่องคุณ

## แบบฝึกหัดท้ายเล่ม

1. แปลง `0x182` เป็นฐานสิบ และเขียน byte ที่เก็บ u32 นี้แบบ little-endian
2. เขียน byte ของ u32 ค่า `1,000,000`
3. หน่วยความจำจำลอง: `[0x1000] = 0x5000`, `[0x5000] = 0x9000`, `[0x9580] = 0xA000`, u32 ที่ `0xA06C` = `777` จงคำนวณ address และค่า runes ของ path `base = 0x1000`, offsets `0, 580, 6C`
4. แยก `0x7FF3A2CBE9DC` เป็น (เลขหน้า, offset ในหน้า) เมื่อ page = 4 KiB
5. `mov rax,[rip+disp32]` อยู่ที่ RVA `0x2000` ยาว 7 byte `disp32 = 0x1F9` target RVA คืออะไร
6. byte `00 00 80 3F` ตีความเป็น float32 ได้เท่าไร และ `0.5` เก็บเป็น byte อะไร
7. อธิบายด้วยคำพูดของตัวเอง ทำไม address `7FF3A2CBE9DC` ใช้ไม่ได้หลังเปิดเกมใหม่ แต่ `eldenring.exe+3B16E30` ใช้ได้
8. ทำไม `is_user_ptr` ควรทิ้ง `0x1234`
9. ถ้า `[CONNECTED]` ขึ้นแต่ attributes ไม่ตรงเมนู บันไดหลักฐานล้มที่ขั้นไหน และควรทำอะไรต่อ
10. ทำไมเราเลือก "ทิ้งทั้ง sample" แทน "รายงานเท่าที่อ่านได้"

**เฉลย**

1. 386; `82 01 00 00`
2. `0xF4240` → `40 42 0F 00`
3. p0 = `[0x1000]` = `0x5000` · p1 = `[0x5000+0]` = `0x9000` · p2 = `[0x9000+0x580]` = `[0x9580]` = `0xA000` · runes ที่ `0xA000+0x6C` = `0xA06C` → **777**
4. เลขหน้า `0x7FF3A2CBE` (หน้าเริ่ม `…CBE000`), offset `0x9DC`
5. `0x2000 + 7 + 0x1F9 = 0x2200`

## Appendix A — อภิธานศัพท์

| ศัพท์ | ความหมายสั้นๆ |
|---|---|
| **Address / virtual address** | เลขที่ระบุตำแหน่งใน address space ของโปรเซสหนึ่ง (ไม่ใช่ตำแหน่ง RAM จริง) |
| **Address space** | ผังที่อยู่ส่วนตัวของแต่ละโปรเซส |
| **AOB (Array of Bytes)** | แพตเทิร์น byte ที่ใช้ค้นโค้ด/ข้อมูล (มีตัวแทน `??`) |
| **ASLR** | การสุ่มย้ายตำแหน่ง module/heap เพื่อความปลอดภัย |
| **Base address (module base)** | ที่อยู่ที่ module ถูก map เข้ามา |
| **Byte / bit** | 8 bit = 1 byte |
| **Dereference** | อ่านค่าที่ address ที่ pointer ชี้อยู่ |
| **EAC** | EasyAntiCheat ระบบ anti-cheat ที่ป้องกันเกมจากโปรแกรมภายนอก |
| **Endianness (little-endian)** | ลำดับ byte ของเลขหลาย byte: byte น้อยมาก่อน (x86-64) |
| **Float32** | ทศนิยม 32 bit (IEEE 754) |
| **Handle** | "บัตรผ่าน" ที่ OS ออกให้ระบุสิทธิ์ต่อ resource (เช่น โปรเซส) |
| **Heap** | พื้นที่ที่โปรแกรมจอง object ตอนรัน |
| **Hexdump** | การแสดง byte เป็นเลขฐานสิบหก |
| **Image** | ตัว exe/DLL ที่ถูก map เข้า memory |
| **Linked list** | รายการที่แต่ละตัวมี pointer ไปตัวถัดไป |
| **MMU / page table** | ฮาร์ดแวร์/ตารางที่แปล virtual → physical address |
| **Module** | exe หรือ DLL ที่ถูกโหลดในโปรเซส |
| **Offset** | ระยะห่างจากจุดตั้งต้น (ต้น struct หรือ base) |
| **Padding** | byte ว่างที่ compiler แทรกเพื่อจัดแนว |
| **Page** | หน่วยของ memory ที่ OS จัดการ (โดยทั่วไป 4 KiB) |
| **PE (Portable Executable)** | รูปแบบไฟล์ exe/DLL บน Windows |
| **Pointer** | ค่าที่เก็บ address ของข้อมูลอื่น |
| **Pointer chain / pointer path** | การ dereference ต่อเนื่องหลายขั้นพร้อม offset |
| **Pointer map** | ดัชนีค่าที่ดูเหมือน pointer ทั้งหมดที่ Pointer Scan สร้างไว้ |
| **Profile** | รายการ offset ที่ผูกกับ exe hash หนึ่งค่าใน `offsets.json` |
| **Process** | โปรแกรมที่กำลังรัน พร้อม address space ของตัวเอง |
| **RIP-relative addressing** | การอ้าง address แบบ "ห่างจาก instruction ถัดไป X byte" |
| **RTTI** | ข้อมูลชื่อชนิดของ C++ ที่ฝังไว้ในไฟล์ |
| **RVA** | Relative Virtual Address ระยะห่างจาก module base |
| **Section (`.text/.data`)** | ส่วนของ exe: โค้ด / ข้อมูล ฯลฯ |
| **Signature scan** | เรียกอีกอย่างว่า AOB scan |
| **SpEffect** | "Special Effect" ตัวแทน buff/debuff/สถานะของตัวละครในเอนจิน |
| **Static address** | address ที่คงที่ต่อ build (module + RVA) |
| **Struct** | กลุ่มฟิลด์ที่เรียงต่อกันใน memory |
| **Torn read** | อ่านข้อมูลที่ถูกแก้ระหว่างอ่าน จนได้ค่าครึ่งเก่าครึ่งใหม่ |
| **vtable / vftable** | ตารางฟังก์ชันเสมือนของ class C++ (pointer อยู่ที่ต้น object) |
