# Phase 1: the params workbench (definition for approval)

_Status: decisions made, step 1.1 passed, step 1.2a (probe) coded and tested, waiting for its run in the game. Part of [roadmap-innovate-spells.md](roadmap-innovate-spells.md)._

## Purpose

Read and write the rows a spell is made of (Goods, Magic, SpEffect, Bullet, AtkParam_Pc, ShopLineup) **in the running game**, so an idea about a spell can be tried before it is baked into `regulation.bin`; and compare a built `regulation.bin` with what the game really loaded.

## What step 1.0 found (facts from the code, the profile and the SpEffect report)

- Today `read`/`write` reach **one** table (`SpEffectParam`, key `effects`) with **4 hand-listed rows** and **6 hand-listed fields** per row, each with a hand-written default for `--reset` (`offsets.json`, `game/params.py`).
- The game keeps each param table as one contiguous file in memory. Header: row count (u16 at +0x0A), data start (u64 at +0x30), then 24-byte row descriptors from +0x40 (id u32, data offset u64 from the head). The same layout holds for every table; only the row size differs. This is measured for SpEffectParam and was assumed for the others in the profile notes.
- The head of SpEffectParam is reached by three static chains found with a Cheat Engine pointer scan: `X = exe+0x4861FB0 -> +0x98 -> +0xE8 -> +0x130`, `Y = exe+0x3D7D568 -> +0x148 -> +0xE8 -> +0x130`, `Z = exe+0x3D85F58 -> +0x4C0 -> +0x80 -> +0x80`. Chains X and Y share their last two offsets, which fits a table of entries where only the first step selects the entry. **Nothing in the repository says where the other tables are**, and the report notes that the table exists in three copies in memory (only the one the chain leads to counts).
- The row sizes and the number of rows of every table are known from the original file: Goods 176 x 2,329; Magic 168 x 317; ShopLineup 52 x 1,296; SpEffect 912 x 11,354; Bullet 272 x 15,475; AtkParam_Pc 456 x 11,017. Field layouts are in `paramdefs.py` for the first four; Bullet is generated by `tools/gen_paramdefs.py` (it was in the reverted T7 work), AtkParam_Pc is not generated yet.
- The reader already accepts a table that an extension grew (rows in a gap before the data); a generic reader must not assume rows are contiguous, only that each descriptor points inside the file.
- A table can be **identified by content** instead of by a measured chain: row count plus a few known ids (Magic: 317 rows and id 4000; Bullet: 15,475 rows and id 10621000; ...). The header check that exists today already proves "this is a param file".

## Design

1. **One reader for rows and fields, two sources.** The same code prints and compares a row from the **running game** and from a **regulation.bin file** (offline). Field names, types and offsets come from the Paramdex layouts already in `paramdefs.py`; nothing is typed by hand per field any more.
2. **Names.** `params.<Table>.<id>.<field>`, for example `params.Magic.6230.mp`. The old names (`params.effects.1621000.effectEndurance`) keep working as aliases, so nothing the author already uses breaks, and `disk-state.json` keeps the old block.
3. **Finding a table.** Chains in `offsets.json` stay the first choice. For a table with no chain the tool uses the probe result (a chain per table, stored in the profile like today). If A turns out to be wrong, the fallback is one Cheat Engine measurement per table, as for SpEffect.
4. **Writing.** Numeric fields (s8..s32, u8..u32, f32); bit fields later. Values are range-checked against the type. Fields that hold an id of another row are writable but marked, and `write` prints a one-line warning (offline use only, as today). No scanning for copies: always through a chain.
5. **`--reset`.** The game's own value, not a hand-written default. Open choice, see below.
6. **Read output.** `read --param Magic.6230` prints every field of a row (name, offset, type, value); `--json` for tools. `read` of the old `params` block stays.
7. **Check against a build.** `read --param-check FILE` compares the rows a built `regulation.bin` added or uses (the commit record lists them) with the same rows in the running game.

## Decisions for the author

1. **Where `--reset` takes the game's own value from.** (a) A snapshot taken at the first read in the session and kept in the session state (simple; lost if the tool is killed before it is saved), or (b) the `regulation.bin` that is in the game folder during the session (exact, also for a built file, but the `game` code then has to read the file, which today only the extension can; it would go through the command layer). Recommendation: (a), with (b) as the later check in 1.4.
2. **Names.** `params.<Table>.<id>.<field>` with the old names kept as aliases (recommended), or only the new ones.
3. **The probe (1.2a).** One read-only command that walks memory from the known global and prints candidates. Go ahead?

## Out of scope

Adding rows in the running game (the tables cannot grow in memory), names and descriptions, anything that needs files inside the game's archives.

## What 1.2b added (2026-10-09)

- `offsets.json` `params.catalog`: one chain per table (the six chains above). Tables are named `Goods`, `Magic`, `SpEffect`, `Bullet`, `AtkParam_Pc`, `ShopLineup`; the game's and Paramdex's names are accepted too, in any letter case.
- `game/paramlayouts.py` (generated by `tools/gen_paramdefs.py` from Paramdex, 1.17.1): every field of the six tables. `game` may not import `extension`, so it has its own copy; a test checks that it agrees with the layouts innovate-items spells uses.
- `game/paramtables.py`: `decode_row` (bytes of a row to fields: signed and unsigned integers, floats rounded as the document does, bit fields) and `Tables` (finds the file, checks the header and that the rows in the file are the layout's size, finds the row by id in the old data or in the gap an extension added).
- `read --param Magic.6230` prints the row as a tree (params > Magic > 6230 > fields), like every other read; `--flat` prints `params.Magic.6230.<field>  value` rows. The same paths are what step 1.3 will accept in `write --set`.
- First run in the game (2026-10-09): Magic 6230, Bullet 10621001, SpEffect 1621000 and the slot-1 Magic row 2230000 (added by the extension: `mp` 90, `refCategory1` 2, `refId1` 21950111, `refId2` 21950211) read correctly.

## What 1.3 added (2026-10-09)

- `write --set params.Magic.6230.mp=10`: any numeric field of any row of the six tables. Ranges are checked against the field's type and bit width (an error, not a clamp). A bit field is changed in its own bit only. An id-like field gets a note.
- The game's own value is saved in `params-snapshot.json` (vault folder) before the first change in a game process, because every `write` is a new process. `--reset` takes a field, a row, a table, a pattern or `all`. A new game process (pid or start time differs) starts with an empty snapshot.
- Old names (`params.effects...`) keep working with the values from `offsets.json`.
- Game result: `Magic.6230.mp` 21 → 10 → `--reset` → 21, each step confirmed with `read --param`.
- Code: `writer/paramedit.py` (names, value checks, snapshot; touches no memory), `writer.py` (`plan_params` splits the two kinds of names, `_tick_catalog` writes and reads back), `commands/write.py` (loads and saves the snapshot).

## What 1.4 added (2026-10-09)

- `read --param-check FILE`: opens a `regulation.bin` (AES, DCX, zstd, BND4; the same code the extension uses, about 5 s), takes every row of the six tables as bytes, reads the same six tables from the game (`Tables.all_rows`: descriptors once, the data in 1 MiB pieces, each descriptor checked like a single-row read), and compares by row id.
- Per table: rows in the file, rows in the game, equal, differing rows with the fields that differ (decoded on both sides), rows on one side only. A difference in bytes that belong to no named field is reported too. `--json` has every difference; the text caps the list (20 rows, 8 fields each). Exit code 0 only when all six tables agree.
- Meaning of a difference: the game was changed after it loaded the file (a `write` in this game process), or the game is not running this file. Check before the first `write` of a game process, or after a restart.
- Code: `commands/paramcheck.py` (file side, comparison, text and JSON), `_param_check` in `commands/read.py`.
- Game result (2026-10-09, slot-1 build): all six tables agree on every row (2330 / 318 / 11356 / 15475 / 11017 / 1297 rows), no difference.
